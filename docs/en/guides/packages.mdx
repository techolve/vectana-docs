title: Registering packages

Vulnerability and EOL checks run against the package versions registered in a project. Register them on the project's "Packages" tab.

## Import a lockfile or SBOM (recommended)

![Packages tab](/screenshots/en/project-packages.png)

Drag and drop a lockfile or SBOM onto the drop area, or click it to choose files. You can import several files at once. CI can also send them automatically ([Register from CI](/guides/ci)).

| File | Type |
| --- | --- |
| `package-lock.json` / `npm-shrinkwrap.json` | npm |
| `pnpm-lock.yaml` | npm (pnpm) |
| `uv.lock` / `poetry.lock` | PyPI |
| `requirements.txt` (and any `.txt` with "requirements" in its name, such as `requirements-dev.txt`) | PyPI |
| `pubspec.lock` | Pub (Dart / Flutter) |
| `go.mod` / `go.sum` | Go |
| `composer.lock` | Packagist (PHP) |
| `Cargo.lock` | crates.io (Rust) |
| `gradle.lockfile` | Maven (Gradle) |
| SBOM: CycloneDX (JSON / XML), SPDX (JSON / tag-value) | Several ecosystems at once (see below) |
| `mise.toml` / `.tool-versions` | Runtimes (registered for [EOL](/guides/eol)) |

:::note
From `requirements.txt`, only lines pinned with `==` (such as `django==4.2.11`) are imported. Ranges like `>=` don't say which version you actually use.
:::

Either `go.mod` or `go.sum` is enough. `go.sum` can still list old versions you no longer use, so `go.mod` (which includes indirect dependencies since Go 1.17) is recommended.

### SBOM

CycloneDX and SPDX SBOMs are recognized by their content, not their name, so call them `bom.json`, `sbom.spdx.json` or anything else. Each component's purl (package URL) is registered as an npm / PyPI / Maven / Go / crates.io / Packagist / RubyGems / NuGet / Pub package.

OS packages (`deb`, `rpm`, `apk`…) and components without a purl are left out; the import tells you how many. For build tools without a lockfile, such as Maven, build an SBOM and import that ([Maven projects](/guides/ci#maven-projects)).

Checking starts in the background right after the import.

### Re-import

Importing a file with the same name again applies **only the differences**:

- Packages that are new are added
- Packages that are gone are removed, together with their findings
- Packages you added by hand are left alone

After updating your dependencies, import the new lockfile. Findings for the old versions disappear and everything is up to date.

:::warning
Differences are tracked by file name. If a monorepo has several files with the same name, such as `frontend/package-lock.json` and `admin/package-lock.json`, importing both into one project makes the second replace the first. Use a separate project for each, or send them from CI with different `source` names ([Several repositories or services in one project](/guides/ci#several-repositories-or-services-in-one-project)).
:::

## Add a package by hand

Under "Add manually", enter the ecosystem, package name and version.

Supported ecosystems are npm, PyPI, Pub, Maven, Go, crates.io, RubyGems, Packagist and NuGet. For Maven, use `groupId:artifactId` (for example `org.springframework.boot:spring-boot`).

## The package list

The list shows each package's ecosystem, name, version, source (manual or the file it came from), last scan time and number of open vulnerabilities. Remove a package with the trash icon.

## When checks run

- Right after you add or import packages
- On a schedule (every 6 hours by default; the interval is a server setting)
- When you press "Scan now" on the project page
